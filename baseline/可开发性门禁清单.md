# 可开发性门禁清单（Definition of Ready）

> 用途：S1 审核阶段逐项打分，决定 PRD 能否放行。
> 等级：**阻断** = 不放行；**重要** = 可放行但必须限期补，且对应 Spec 相应位置留 `[待澄清]`；**建议** = 记录不阻塞。
> 设计来源：改编自 AWS Labs AI-DLC，新增了 ★ 的「角落收敛」与「来源标注」两部分。

## ★ 贯穿全表的两条铁律

**铁律一：三态收敛。**
每一个被识别出的问题点——无论来自哪一类检查项，还是来自角落叉乘扫描——**必须收敛为三者之一**：
1. 写成一条需求或一条可判定的验收标准；
2. 记为「假设 + 理由」（说明为什么不需要单独一条需求）；
3. 明确列入「不在范围」。

**沉默的问题点 = 上线后坏掉的那一个。** 不允许"先记着"、"后面再说"、"到时候看"。

**铁律二：来源标注。**
完善后的 PRD 里，每一段实质内容（段落 / 列表项 / 表格行）都必须带来源标签。
无来源但值得保留的内容只能进《假设确认清单》并标 `[assumption]`，且**必须经 PM 确认**才可继续。
"行业惯例""我推测""常识"都不是来源。

## A. 业务完整性
| 编号 | 检查项 | 等级 |
|---|---|---|
| A1 | 每个功能有明确的入口与出口（谁、从哪进、做完到哪） | 阻断 |
| A2 | 每个功能的业务价值/目标可一句话说清 | 建议 |
| A3 | 所有涉及的角色与权限已定义 | 阻断 |
| A4 | 业务规则写清例外分支（超时、并发、重复提交、取消） | 阻断 |
| A5 | 无「等等 / 若干 / 根据实际情况 / 视情况而定」这类模糊表述 | 阻断 |

## B. 流程与状态
| 编号 | 检查项 | 等级 |
|---|---|---|
| B1 | 所有业务对象状态已穷举 | 阻断 |
| B2 | 状态迁移的触发条件与结果明确 | 阻断 |
| B3 | 无孤立状态、无未定义迁移 | 阻断 |
| B4 | 失败的流程有回退/补偿路径 | 阻断 |

## C. 数据与字段
| 编号 | 检查项 | 等级 |
|---|---|---|
| C1 | 所有实体字段有名称、类型、是否必填 | 阻断 |
| C2 | 枚举字段给出完整取值列表（不能写"等"） | 阻断 |
| C3 | 字段长度/范围/精度约束明确 | 重要 |
| C4 | 数据来源与归属明确（谁产生、谁可改） | 重要 |
| C5 | 敏感数据与可见范围明确 | 重要 |
| C6 | ★「未知」与「零」在全链路中可区分 | 重要 |
| C7 | ★ 金额不用浮点；单位恒随数量出现 | 重要 |

## D. 交互与文案
| 编号 | 检查项 | 等级 |
|---|---|---|
| D1 | 每个页面/弹窗的元素构成可推导 | 阻断 |
| D2 | 关键操作的结果反馈明确（成功/失败/部分成功） | 阻断 |
| D3 | **文案字样给出具体内容**，不能只写"提示错误信息" | 阻断 |
| D4 | 空态、加载态、错误态的描述存在，且是**三个不同的视图** | 重要 |
| D5 | 动效/过渡有说明或明确"无动效" | 建议 |
| D6 | ★ 破坏性操作有确认（指明影响范围）或撤销 | 重要 |
| D7 | ★ 状态不只靠颜色表达；功能可用键盘完成 | 建议 |

## E. 接口契约可行性
| 编号 | 检查项 | 等级 |
|---|---|---|
| E1 | 界面要展示的每项数据都能对应到可获取的数据来源 | 阻断 |
| E2 | 列表分页、排序、筛选规则明确 | 阻断 |
| E3 | 需要实时/推送的场景已说明 | 重要 |
| E4 | 第三方依赖与失败降级已说明 | 重要 |
| E5 | ★ 部分来源失败时的响应形态明确（部分成功 ≠ 完整） | 重要 |
| E6 | ★ 每次外部调用有超时；重试不产生重复副作用 | 重要 |

## F. 埋点
| 编号 | 检查项 | 等级 |
|---|---|---|
| F1 | 核心业务漏斗的关键节点可识别 | 重要 |
| F2 | 埋点上报时机与去重规则明确 | 建议 |
| F3 | ★ 未登录等边界态下的用户标识取值明确 | 建议 |

## G. 验收标准
| 编号 | 检查项 | 等级 |
|---|---|---|
| G1 | 每个功能有可判定的验收标准（可勾选，不写"正常"） | 阻断 |
| G2 | P0 主流程的验收路径完整 | 阻断 |
| G3 | ★ QA 能仅凭这些验收标准写出测试用例 | 阻断 |

## ★ H. 角落收敛（核心新增）
| 编号 | 检查项 | 等级 |
|---|---|---|
| H1 | 已按 `baseline/角落检查清单.md` 做「组件 × 条件面」叉乘扫描 | 阻断 |
| H2 | 每个适用条件都已收敛为「需求 / 假设+理由 / 明确排除」三态之一 | 阻断 |
| H3 | 《角落扫描表》非空且覆盖全部组件 | 阻断 |
| H4 | 扫描前已确定部署形态（单/多用户、单/多租户、是否涉合规） | 重要 |

## ★ I. 来源与假设
| 编号 | 检查项 | 等级 |
|---|---|---|
| I1 | 已建立来源注册表，且注册项真实可查 | 阻断 |
| I2 | 完善后 PRD 中无「无来源标签」的实质段落 | 阻断 |
| I3 | 所有 `[平台补充]` 与 `[assumption]` 都进了《假设确认清单》 | 阻断 |
| I4 | 假设清单无空白未选项（全部 Accept 或 Convert） | 阻断 |

## 判定规则
- **存在任一「阻断」项 → 状态置为「待PM补充」，禁止进入拆解阶段。**
- 「重要」项的补齐期限与责任人要记录在案。
- 复审时只重查前次未过项 + 被 PM 改动波及的条目。
- 复审循环次数受上限约束（见 `platform/平台需求概要.md`），超限则升级处理。

## 输出格式
| 检查项 | 等级 | 结论(通过/不通过) | 证据（原文位置） | 完善建议 or 待澄清编号 |
|---|---|---|---|---|
| A1 | 阻断 | 不通过 | §2.3 | [待澄清-Q1] |
