# 门店补货申请 App · 产品需求文档（PRD）

版本：v1.0 ｜ 状态：待评审

## 1 背景与一句话说明

**一句话说明**：让连锁门店店长在手机上提交「补货申请」，总部采购按申请单审核、下发，替代目前微信群 + Excel 的人工流转。

**背景**：现有 320 家门店补货靠微信群接龙和 Excel 汇总，平均 2.5 天才能形成一张采购单；漏报、重报、串号每周约 18 起；总部无法按门店统计缺货率。本产品把「申请 → 审核 → 下发」搬到线上，目标把补货周期压到 4 小时内。

**目标用户**：门店店长（提交）、区域督导（初审）、总部采购（终审与下发）。

## 2 主流程与分期规划

**主流程**（一条主链路，无分支）：
1. 店长在首页点「新建补货申请」→ 选商品 → 填数量 → 提交。
2. 提交后单据进入「待初审」，推送给该门店所属区域督导。
3. 督导在列表里初审：通过则进入「待终审」；驳回则回到「已驳回」并附驳回原因。
4. 总部采购终审：通过则进入「已下发」；驳回则回到「已驳回」。
5. 已下发的单据在「我的申请」里只读展示，不再允许修改。

**分期规划**：
- **第一期（本期）**：新建申请、初审、终审下发、我的申请列表与详情、消息通知。
- **第二期（本期不做）**：库存自动补货建议、批量导出、门店间调拨。
- **第三期（本期不做）**：对接 ERP 自动生成采购单。

## 3 需求范围与边界

**本期范围内**：申请单的创建 / 查看 / 初审 / 终审 / 下发；角色与数据隔离；消息通知；操作留痕。

**本期范围外（明确不做，避免误实现）**：商品主数据维护（只读引用）；库存数量扣减；支付与结算；退货流程；Web 端（仅 Android App）。

**边界规则**：一张申请单最多 50 个商品明细；单个商品数量 1~9999 的整数；申请单提交后除「驳回后可再次提交」外不可编辑。

## 4 状态机与迁移条件

申请单状态穷举为 6 个，无其它状态。

| 状态码 | 名称 | 可执行动作 | 迁移到 | 迁移条件 |
|---|---|---|---|---|
| `draft` | 草稿 | 编辑 / 提交 / 删除 | `submitted` / 删除 | 提交时明细 ≥1 且所有数量合法 |
| `submitted` | 待初审 | 初审通过 / 初审驳回 / 撤回 | `reviewing` / `rejected` / `withdrawn` | 仅督导可操作；撤回仅店长本人且未进入终审 |
| `reviewing` | 待终审 | 终审通过 / 终审驳回 | `issued` / `rejected` | 仅采购可操作 |
| `issued` | 已下发 | 无（只读） | — | 终态 |
| `rejected` | 已驳回 | 再次提交 / 删除 | `submitted` / 删除 | 仅店长本人；再次提交须修改至少一个明细 |
| `withdrawn` | 已撤回 | 再次提交 / 删除 | `submitted` / 删除 | 仅店长本人 |

**终态**：`issued`、`withdrawn`、`rejected` 三个状态不可再流转到 `reviewing`/`submitted`，只能由本人重新提交产生**新单据**（旧单据保留供追溯）。

## 5 异常与失败路径

| 场景 | 系统行为 | 用户可见文案 |
|---|---|---|
| 提交时无网络 | 本地保留草稿，不丢数据 | 「网络不通，已存为草稿，联网后自动重试」 |
| 提交时同一张单被连点 | 前端 3 秒内只提交一次；服务端按幂等键去重 | 无（静默去重） |
| 商品主数据加载失败 | 页面展示重试按钮，不展示旧缓存 | 「商品加载失败，点这里重试」 |
| 审核时单据已被他人处理 | 拒绝本次操作并刷新最新状态 | 「这张单已被处理，已为你刷新」 |
| 图片/附件上传中断 | 单张重试，不影响其它张 | 「第 2 张上传失败，重试」 |
| 消息推送失败 | 不阻塞业务，进 App 时用红点补偿 | 无（静默补偿） |
| 服务端 5xx | 不修改本地状态，可重试 | 「服务开小差，请稍后再试」 |

## 6 数据与字段定义

**申请单 `RestockOrder`**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `order_id` | string | 是 | 服务端生成，全局唯一 |
| `store_id` | string | 是 | 门店 ID |
| `status` | enum | 是 | 见第 4 节 6 个状态 |
| `total_quantity` | int | 是 | 明细数量之和，服务端计算 |
| `item_count` | int | 是 | 明细条数，≤50 |
| `remark` | string(≤200) | 否 | 备注 |
| `reject_reason` | string(≤200) | 否 | 驳回时必填 |
| `created_at` / `updated_at` | ISO8601 | 是 | 时间戳 |
| `created_by` / `reviewed_by` / `issued_by` | string | 否 | 操作人 |

**明细 `RestockItem`**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `item_id` | string | 是 | 明细 ID |
| `order_id` | string | 是 | 所属申请单 |
| `sku_id` | string | 是 | 商品 SKU |
| `sku_name` | string | 是 | 快照，冗余存储 |
| `quantity` | int | 是 | 1~9999 |
| `unit` | string | 是 | 单位，如「箱」 |

**门店 `Store`**：`store_id`、`name`、`region_id`（决定初审督导）、`manager_user_id`、`status`（`active`/`disabled`）。

**用户 `User`**：`user_id`、`name`、`role`（`manager`/`supervisor`/`buyer`）、`region_id`（督导所属区域）。

## 7 字段校验与约束

| 字段 | 规则 | 违反时提示 |
|---|---|---|
| `quantity` | 必填，整数，1 ≤ q ≤ 9999 | 「数量需填 1~9999 的整数」 |
| `item_count` | ≤ 50 | 「一张单最多 50 个商品」 |
| `remark` | ≤ 200 字，可空 | 「备注最多 200 字」 |
| `reject_reason` | 驳回时必填，≤200 字 | 「请填写驳回原因」 |
| `sku_id` | 必须存在于商品主数据 | 「该商品已下架」 |
| 重复商品 | 同一单内 `sku_id` 不可重复 | 「该商品已添加过」 |
| 门店状态 | `disabled` 门店不可提交 | 「该门店已停用，请联系管理员」 |

## 8 页面级元素与文案

**页面 1 · 首页**：标题「补货申请」；主按钮「新建补货申请」；列表项（单号 / 状态标签 / 商品数 / 提交时间）；空态「还没有补货申请，点上方按钮新建」。

**页面 2 · 新建申请**：商品选择器（搜索框占位「搜索商品名称或编码」）；明细行（商品名 / 数量输入框 / 删除）；底部「添加商品」与「提交」；提交二次确认「确认提交这张申请单？」。

**页面 3 · 申请详情**：顶部状态标签；明细只读列表；底部按钮按角色与状态变化（督导看「通过」「驳回」，采购看「下发」「驳回」，店长看「撤回」「再次提交」）。

**页面 4 · 待我处理**：Tab「待初审」「待终审」；列表项右侧显示「去处理」。

**文案字样**：状态标签固定为「草稿 / 待初审 / 待终审 / 已下发 / 已驳回 / 已撤回」；所有按钮为 2~5 字动宾结构；错误提示不超过 20 字。

## 9 平台接口契约

统一前缀 `/api/v1`，统一响应包 `{code, message, data, request_id}`。

| 编号 | 方法 | 路径 | 说明 | 主要错误码 |
|---|---|---|---|---|
| API-01 | POST | `/restock-orders` | 新建申请（支持 `Idempotency-Key`） | 400 参数非法 / 409 幂等冲突 |
| API-02 | GET | `/restock-orders` | 列表，分页 `page/page_size`（20/50/100），筛选 `status` | 400 分页越界 |
| API-03 | GET | `/restock-orders/{order_id}` | 详情 | 403 非本人且非审核人 / 404 不存在 |
| API-04 | PATCH | `/restock-orders/{order_id}` | 编辑（仅 `draft`/`rejected`），带 `If-Match` | 409 版本冲突 / 400 状态不允许 |
| API-05 | POST | `/restock-orders/{order_id}/submit` | 提交 | 400 明细为空 / 409 状态不允许 |
| API-06 | POST | `/restock-orders/{order_id}/review` | 初审，body `{action: approve\|reject, reason?}` | 403 非督导 / 409 已被处理 |
| API-07 | POST | `/restock-orders/{order_id}/issue` | 终审下发 | 403 非采购 / 409 已被处理 |
| API-08 | POST | `/restock-orders/{order_id}/withdraw` | 撤回 | 403 非本人 / 409 已进入终审 |
| API-09 | GET | `/skus` | 商品主数据（只读），支持 `q` 搜索 | 400 关键字过长 |

**鉴权**：所有接口需登录态；**逐对象鉴权**：越权与不存在统一返回 403，避免泄露对象是否存在。
**分页与排序**：`created_at` 倒序，稳定排序（同秒按 `order_id` 兜底）。

## 10 角色与权限矩阵

| 能力 | 店长 manager | 督导 supervisor | 采购 buyer |
|---|---|---|---|
| 新建 / 编辑草稿 | ✅（仅本门店） | ❌ | ❌ |
| 提交 / 撤回 | ✅（仅本人单据） | ❌ | ❌ |
| 查看申请单 | ✅（仅本门店） | ✅（仅本区域） | ✅（全部） |
| 初审通过 / 驳回 | ❌ | ✅（仅本区域） | ❌ |
| 终审下发 | ❌ | ❌ | ✅（全部） |
| 查看驳回原因 | ✅ | ✅ | ✅ |

**数据隔离规则**：店长只能看到 `store_id` 等于自己的单据；督导只能看到 `region_id` 等于自己的单据；采购可见全部。越权访问一律 403。

## 11 生成与验证

- 本 PRD 用于驱动「原生 Android 代码生成」；生成物为 Kotlin + XML 源码工程，**平台不做服务端构建**，交付 ZIP 内不含 APK。
- 生成后做**静态 L1 校验**：XML 可解析、工程结构合法、元素 ID 与元素树一一对应、属性取值在域内、资源引用完整。
- 真实编译（Gradle）由使用方在本机执行；L2 构建证据由受信的本地构建代理上报。

## 12 角落收敛

- 同一门店同一 SKU 在同一天内重复提交：允许，不做去重（业务上会合并采购）。
- 单据在审核中被撤回：仅店长本人且状态仍为 `submitted` 时允许；已进入 `reviewing` 不允许。
- 门店被停用后未提交的草稿：仍可查看与删除，不可提交。
- 分页边界：`page` 超出总页数返回空数组而非报错；`page_size` 仅允许 20/50/100。
- 时钟与时区：全部时间以服务端 UTC 存储，客户端按本地时区展示。
- 并发：两人同时审核同一张单，后到者收到 409 并自动刷新。
