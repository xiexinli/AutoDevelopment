## 1 大模型：改为标准 OpenAI 兼容，不再自造网关协议

原实现假设上游提供 `/v1/review`、`/v1/split` —— 真实上游（OpenAI / DeepSeek / 本机 LM Studio…）不具备。
现改为 `POST {AD_LLM_BASE_URL}/chat/completions`：

| 项 | 实现 |
|---|---|
| 配置 | `AD_LLM_BASE_URL` + `AD_LLM_MODEL`（+ 可选 `AD_LLM_API_KEY`）；**不配 = fail-closed** |
| JSON 约束 | **默认不发 `response_format`**（`AD_LLM_JSON_MODE` 可选 `json_object`/`json_schema`） |
| 结构校验 | 空/畸形审核结论、非五角色需求包、编号不合规 **一律判上游失败，绝不静默放行** |
| 超时 | 默认 **60s**（`AD_LLM_TIMEOUT_MS` 可覆盖），**覆盖「请求 + 响应体 + 流式读取」** |
| 重试 | 退避 + 抖动 ≤2 次；**4xx 不重试**；JSON 解析/结构失败**再给一次机会**（上游截断很常见） |
| 取消 | 调用方 `signal` 贯穿上游，**原样上抛 AbortError**，不被翻译成 `failed`/`timeout` |
| 流式 | `stream:true` 增量直接转 SSE `chat.delta`（**真流式**）；上游不支持时自动退回一次性返回 |

## 4 接真实上游暴露并修掉的真实缺陷

1. **`response_format: json_object` 被上游 400**（LM Studio 新版只接受 `json_schema`/`text`）→ 默认不发该字段，靠提示词 + 结构校验保证 JSON。
2. **超时只包住 `fetch()` 不够**：上游回完响应头就挂住不写 body 时，`await res.text()` **不会**被那次 abort 打断，实际要等 undici 自己的 300s body 超时（表现为「5 分钟才失败」且错误是 `TypeError: terminated`）。→ 改为**同一个 deadline 贯穿请求、响应体与流式读取**。测试从 301011ms 降到 5784ms。
3. **流式取消同理**：`reader.read()` 必须用同一个 signal 才能被中断，否则取消会变成「流式返回为空」。
4. **`Content-Type: application/json` + 空 body 被 Fastify 直接 400**：契约里 `#12` 触发解析、`#44a` 取消、`#55` 打版本等 POST 都**无请求体**，客户端带 content-type 不带 body 很常见 → 空 body 视为 `{}`（非空但非法 JSON 仍 400）。
5. **docx 内嵌电子表格的 token 形如 `<spreadsheetToken>_<sheetId>`**，整串当 spreadsheet token 会 400 → 按最后一个下划线拆开取区间。
6. **长文档下模型可能截断 JSON** → JSON 任务解析失败再给一次机会（仍失败才判失败）。
7. **`--watch` 旧进程会抢回端口**：实测出现「以为在跑真实上游、实际跑在开发桩上」的假象（Spec 正文里写着「由开发适配器生成」才发现）。**长任务必须单实例、非 watch。**
8. `AD_TASK_TIMEOUT_MS`：本机大模型单次 40s+，5 份 Spec 串行会超契约的 5min 上限 → 提供覆盖项（**生产按契约**）。

- `PUT /api/v1/me/llm-model` 保存选择，**按用户隔离**（`tbl_user_pref`），**未选择时用目录里的第一个可用模型**；
- 顶栏新增「模型」选择器；审核页评分卡标题显示 `模型：<id>`，让用户看得见「这次是谁判的」。

模型清单**不写死在平台代码里**：来自目录文件 `server/data/llm-catalog.json`（`AD_LLM_CATALOG_FILE` 可覆盖），
本机由 `server/tools/gen-llm-catalog.mjs` 从 DHwork 客户端配置生成；`run-local.sh` 在目录缺失时自动生成。

`--probe` 会逐个真调一次以核实可用性。本机实测 15 项中 **14 项可用**，
唯一不可用的是 `Auto`（DHwork 的自动路由项，直接当模型名调用会被上游拒绝）—— 它**仍然展示**给用户，但置灰并写明原因。

⚠️ 探测本身踩过两个坑，都已修正（否则会**把可用模型误判成不可用**）：
`max_tokens` 不能取 1（gpt-5.x/6.x 会以「低于最小值」400）；**429 与超时属于瞬时/不确定**，不等于模型不存在。

## 10 登录方式：本地账号 + 密码（`#72`，2026-10-21）

飞书扫码登录需要企业主体（见 §5），本地开发不便。因此新增**本地账号密码登录**：

- `GET /auth/methods` 回报可用的登录方式（`password_login` / `feishu_login`），**前端据此决定默认展示哪种**；
- `POST /auth/password/login` `{username, password}` → 签发平台 token；
- 前端登录页改为**分栏**：「账号密码」（默认）/「飞书扫码」，两种方式都保留。

**安全约定**（不因「反正是本地」而放松）：
- 密码**只存 scrypt 加盐哈希**（`scrypt$salt$hash`），永不落明文、不进日志 —— 实测库中字段不含明文；
- 校验用 `timingSafeEqual`；账号不存在时**照样跑一次哈希**，避免用响应时间枚举账号；
- 「账号不存在」与「密码错误」返回**同一个** `UNAUTHENTICATED` 与同一句文案（实测两者完全一致）；
- 非法用户名（`<2` 或 `>32` 位、含空格/中文）→ `INVALID_ARGUMENT`。

**开关**：`AD_PASSWORD_LOGIN=development` 启用（**未设置即关闭**，fail-closed）；
开发密码来自 `AD_DEV_PASSWORD`，**只写在 gitignored 的 `server/.env`，不进版本库**。
`development` 模式下「任意合法用户名 + 开发密码」可**自助开通**（本地便利），
错密码**不会**开通账号（有回归断言）。初始账号 `AD_DEV_USERNAME`（默认 `admin`）映射到既有演示用户，
这样本机已有项目立刻可见。

⚠️ **这是阶段性的本地登录方式**：`AD_PASSWORD_LOGIN` 是环境变量开关，不是权限系统；
生产必须设为 `disabled`，改用企业自建应用扫码或你们自己的账号体系。
