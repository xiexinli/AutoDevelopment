## 1 接口层：契约 75 个 vs 代码实现

**方法**：正则抽取 `接口契约 §1` 各表的方法/路径 → 归一化参数名（`{project_id}` / `:project_id` → 同一形态）→ 与 `app.get/post/put/patch/delete/route` 的实际注册逐一比对。
（脚本可复跑；`app.route({method,url})` 形式的动态注册**需单独识别**，见 §1.2）

| 项 | 数 |
|---|---|
| 契约声明端点（含一号多方法） | **81** |
| 代码实际注册路由 | **83** |

### 1.1 契约有、代码无 —— **0 处（初始 3 处经核为扫描器盲区）**

首轮扫描报 `#37 PATCH /elements/{element_id}`、`#39 PUT /elements/{element_id}/style`、`#40 PUT /elements/{element_id}/events` 缺失。
**复查后确认是假阳性** —— 三者由 `editor.ts` 用**循环动态注册**实现：

```ts
for (const suffix of ['', '/style', '/events'] as const) {
  const method = suffix ? 'PUT' : 'PATCH';
  app.route({ method, url: `/api/v1/elements/:element_id${suffix}`, handler: ... });
}
```

→ 结论：**契约声明的接口，代码全部存在**。`#37`/`#39`/`#40` 的 `If-Match`（乐观锁）也在该循环内统一 `assertIfMatch`。

### 1.2 代码有、契约无 —— 4 处（1 处为解析假阳性）

| # | 方法 路径 | 判定 |
|---|---|---|
| 1 | `PUT /pages/{page_id}/draft` | **假阳性**：契约 `#42` 写作 `GET \`/pages/{page_id}/draft\` / \`PUT\``，是同一编号下的两个方法，非缺口 |
| 2 | `POST /auth/feishu/qrcode/{state}/simulate` | **开发适配器专用**，有意不进契约（真实环境由手机扫码推进；`B5-真实上游接入验收记录` §2 已说明） |
| 3 | `GET /projects/{project_id}/kb-sectors` | ⚠️ **契约未登记**（知识库页面的「板块」列表）—— 实现存在、契约与接口-Spec §1.2 均无对应编号 |
| 4 | `GET /projects/{project_id}/tasks` | ⚠️ **契约未登记**（项目任务列表；契约 §0.4 只登记了 `GET /tasks/{id}` 与 SSE `stream`） |

> 3、4 不影响功能，但按平台自己的口径属于「**契约未覆盖的实现**」，建议下一轮补编号或明确标注为内部接口。

## 2 REQ 层：RTM 五列引用的产物是否真实存在

**方法**：逐行解析 RTM 主表 91 行，把「UI 页面 / 接口 / App 路由 / 埋点事件 / 测试用例」五列里引用的每个 ID，拿到对应文档的**全量 ID 集合**里做存在性校验（反向孤儿检测）。

| 检查 | 结果 |
|---|---|
| RTM 主表行数 | **91**（另 3 行为汇总/异常说明） |
| 五列引用的 UI / RT / EVT / TC ID 全部存在 | ✅ **是**（首轮报的 2 条为假阳性：`EVT_llm_model_switch`、`EVT_auth_password_login` 出现在「测试用例」列的括注里，非误引用） |
| 契约接口中被任何 REQ 引用 | **75 / 75** |

### 2.1 发现的真实遗漏（**已修**）

**`#3`（`GET /projects/{project_id}` 项目详情）在 `接口-Spec §5.4` 挂 `REQ-PROJ-002`，但 RTM 的 `REQ-PROJ-002` 行接口列只写了 `#1`** —— 即「接口 → REQ」与「REQ → 接口」两个方向**不一致**，导致 `#3` 在反向检测里成为**唯一孤儿**。

已修：`baseline/需求追溯矩阵.md` 的 `REQ-PROJ-002` 行接口列补 `#3`（项目详情）。修后**接口孤儿 = 0**。

> 说明：这是**文档间的不一致**，不是代码缺口（接口本身实现完好、测试也覆盖）。但按 RTM 自己的口径（孤儿必须为 0）它是一处真实缺陷。

## 3 结论

| 结论 | 证据 |
|---|---|
| **没有「声称实现、实际没实现」的接口** | 契约 81 个端点 → 代码全部存在（`app.route` 动态注册已单独识别） |
| **没有「声称有、实际没有」的 REQ 产物** | RTM 91 行 × 五列引用 → 全部命中对应文档的 ID 集合 |
| **接口孤儿 0** | 修 `#3` 遗漏后，75 个接口全部被 ≥1 条 REQ 引用 |
| **契约外实现 4 处** | 2 处为开发/解析性质（可不登记），2 处（`kb-sectors`、`tasks` 列表）建议补登记 |

**因此，此前「零遗留」的说法在接口与 REQ 两个层面**从「文档自证」升级为**「经机器比对」**。
仍未覆盖的层面（本报告**不**声称已核）：**UI 元素 ↔ App 落点的语义正确性**（只核了 ID 存在性，未核语义是否真的对得上）、**测试用例的实际可执行性**（只核了编号存在性）。
