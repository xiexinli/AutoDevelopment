## 二、真缺陷：声明与实现不符

### S1 `#3` 项目详情 **不返回 `owner_user_id`**

- **声明**：`接口-Spec §5.5.3` 出参含 `owner_user_id`；`接口契约 §1.1` 同
- **实现**（`server/src/routes/projects.ts`）：返回 `project_id/name/description/stage/depth/version/current_revision_id/current_version_id/created_at/updated_at` —— **没有 `owner_user_id`**
- **实测**：`GET /projects/p_mvhyf0960002xr0l` 的 DB 里 `owner_user_id = ou_dev_user`（**有值**）→ 响应里**依然没有该键**
- **影响**：前端 `web/src/domain/types.ts` 的 `Project` 类型**声明了 `owner_user_id: string`**，但运行时永远拿不到（当前无页面读取它，所以没炸；属**契约违约 + 类型说谎**）

### S2 `#3` 的 `current_revision_id` / `current_version_id` **为 null 时键直接消失**

- **声明**：`接口-Spec §5.5.3` 明确写「未产生时为 **`null`**」（→ 键必须存在）
- **实现**：`current_revision_id: row.current_revision_id ?? undefined` —— `undefined` 会被 `JSON.stringify` **丢掉整个键**
- **实测**：
  - 有 revision 的项目 → 键存在（`"rev_mvhyimgg0028roen"`）✅
  - `current_version_id` 为 null → **键不存在**（不是 `null`）❌
- **影响**：调用方按契约判 `data.current_version_id === null` 会得到 `undefined`；`undefined === null` 为假 → **「尚无版本」分支永远走不到**

### S3 `#6` 工作台状态条 **字段名与嵌套结构都与声明不符**

| 声明（`§5.5.4`，注明「字段名冻结见 §5.0.3」） | 实现（`server/src/routes/projects.ts`） |
|---|---|
| `data.gate_status`（enum） | ❌ 无此键；实际是 `gate.verdict` |
| `data.gate_counts.blocking` / `.major` / `.suggestion` | ❌ 无 `gate_counts`；实际是 `gate.blocking_count` / `gate.major_count`，**且没有 `suggestion`** |
| `data.current_version_id`（string 36） | ❌ 无此键 |
| `data.current_version_seq`（int） | ⚠️ 实际是 `version_seq` |
| （未声明） | ➕ 实际多出 `running_tasks` |

- **实测响应**：`{"stage","version_seq","running_tasks","loopback_round","gate":{"verdict","blocking_count","major_count"}}`
- **影响**：**按 Spec 写前端就取不到值**；且 `suggestion` 计数在实现里**根本不存在**（工作台无法展示「建议」数）

### S4 `#5` `DELETE /projects/{project_id}` **不校验二次确认**（破坏性操作可一次误删）

- **声明**：`接口契约 §1.1` 把 `#5` 标为 **`⬛`**，而 `⬛` 的定义写在本文件表头：**破坏性操作（必须二次确认，服务端亦须校验）**
- **实现**：直接 `UPDATE tbl_project SET deleted_at = ...`，**没有任何 `confirm` 校验**
- **对照**：同类破坏性接口**都做了**校验 —— `#38` 元素删除要 `confirm=true`、`#53` 接口删除要 `confirm:true`、`#70` 中止要 `confirm:true`
- **实测**：`DELETE /projects/{id}`（不带任何 confirm）→ **200 OK，项目被删**
- **影响**：一次误请求即触发逻辑删除（30 天后物理清除）

## 三、声明不完整（实现没错，是**契约写得不够**）

### S5 `#7` 列表声明含 `doc_type`，实现只返回 `origin`

- **声明**：`§5.4 #7` → `items[]（title/doc_type/origin/updated_at）`；实体 `E2 KbDoc` 确有 `doc_type` 字段
- **实现**：`kb_doc_id/document_id/title/sector/origin/version/created_at/updated_at` —— **无 `doc_type`**
- **判定**：要么实现漏返回、要么声明多写；**两者必有一错**（建议对齐到 `sector`+`origin` 并修声明）

### S6 `#62` 请求体 `schema_version` **未声明类型**，实现却强制 string

- **声明**：`请求体 {schema_version, batch:[…]}` —— **没写类型**
- **实现**：`typeof body.schema_version !== "string"` → 非字符串一律 400
- **实测**：传 `{"schema_version": 1}`（数字）→ `400 INVALID_ARGUMENT「schema_version 不能为空。」`；传 `"1.0"` → 200 `{schema_version, accepted, rejected[]}`
- **影响**：调用方按字面把 `schema_version` 写成数字是**大概率事件**，且报错文案（「不能为空」）**误导**（明明是类型错）
