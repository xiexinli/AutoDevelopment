## 1 平台主流程（对话式，含人工回流）

```
[S0 建项目 + 建知识库]   新建项目、建立完整知识库（术语/领域/组件/规范）
        │
        ▼
[S1 PRD 上传与解析]      网页上传 docx / md / 飞书链接；正文+内嵌表格+白板补取
        │
        ▼
[S2 细化完善 + 门禁]     PRD审核完善Agent
        │                ├─ 细化完善：补全缺漏，消除阻断业务点
        │                ├─ 门禁判定：对照 baseline/可开发性门禁清单.md
        │                └─ 输出《完善建议》+《待澄清问题清单》(按阻断等级)
        │
   ┌── 有阻断项？──┐
   │ 是            │ 否
   ▼               │
[S3 对话式补充完善] │  ★ 右栏聊天框：平台追问、需求方用自然语言回答
   │  回填写回原PRD │     （不再要求填表；补充内容写回原 PRD，留快照）
   └────►回 S2 复审─┘   （默认最多 3 轮，超限升级为「接受并记录 / 中止」）
        │
        ▼
[S4 需求拆解]            角色需求包（粗粒度、带 REQ-ID）；★ 埋点方案在此定义
        │
        ▼
[S5 角色 Spec 生成]      主流程顺序：初版 UI ──► 接口 ──► 安卓 App ──► 测试
        │                （本期目标端固定安卓；iOS/跨平台属远期）
        │                交付格式统一 Markdown（.md）
        ▼
[S6 角色校对]            校对Agent：按各角色特点核对，输出《补充要求清单》
        │                补不上的 → 回流 S3 继续对话问 PM
        ▼
[S7 落到工程]            ★ 手机样式编辑区域（与左侧预览是同一区域的两个状态）：
        │                  拖拽控件 → 选中控件调全量样式(宽高/背景色/字体颜色/字体大小/
        │                  内外边距/圆角/边框/透明度/对齐/可见性) + 配事件(点击/长按/双击)
        │                  → 直接生成原生安卓代码
        │                  控件白名单尽可能全（见 platform 文档 F13）
        │                  对应关系靠「元素 id」（项目内全局唯一 EL-<模块>-<三位>）
        │                + 接口增删改查与版本控制（项目整体版本）
        │                + 能力自选（默认集：推送/性能采集/崩溃/日志/统计/加固/隐私弹窗，默认全关）
        │                + 埋点在本阶段写入代码
        │                ★ 左侧预览：agent 生成并验证完成后刷新为当前代码页面
        ▼
[S8 测试]                接口 / App / 埋点 三层 + E2E 串联；埋点在本阶段验证
        │
        ▼
[S9 交付归档]            各角色独立 Markdown Spec + 需求追溯矩阵 + 安卓工程 + 版本归档
```

**两个关键点：**

1. **S2↔S3 是循环门禁**，PRD 不达标就不放行，不允许"带着阻断问题往下生成"。
2. **S3 是对话，不是表单**——需求方在聊天框里补充，平台负责把它变成 PRD 的正式条款。

## 3 五个角色与依赖顺序

用户原话定义了接口的定位：**「必须满足 UI 展示及交互所需的数据」**——这决定了执行顺序不能并行：

> ✅ **2026-10-20 已定**：本期**目标端只做安卓**；**埋点不再单独占流程阶段**——方案在拆解阶段定义、
> 代码在安卓开发阶段写入、验证在测试阶段进行。下表仍是完整的 5 角色视图（埋点仍单独出一份 Spec）。

| 顺序 | 角色 | 为什么在这个位置 |
|---|---|---|
| 1 | **UI** | 定义元素/交互/动效/文案，是所有下游的数据需求源头 |
| 2 | **接口** | 由 UI 明确「每个元素要显示什么数据」倒推字段与格式 |
| 3 | **App** | 把 UI 与接口**绑成对应关系**，产出可实现级详细需求 |
| 4 | **埋点** | 依赖 UI 元素（曝光点）+ App 动作（点击点） |
| 5 | **测试** | 依赖全部，产出接口/App/埋点三层用例 |

> 接口 Spec 里必须有一张《UI 数据供给对照表》：每个 UI 元素 → 需要的数据 → 来源接口与字段 → 是否满足。这是"接口服务 UI"的强制证据。

## 4 统一约定

1. **编号**：需求 `REQ-<模块>-<三位>`；UI 元素 `EL-<模块>-<三位>`、页面 `UI-…`；接口 `API-…`；App 路由 `RT-…`；埋点事件 `EVT_<模块>_<动作>`；测试用例 `TC-…`。
   ★ **元素 id 必须项目内全局唯一**，它是「网页拖拽控件 ↔ 原生安卓控件 ↔ 埋点曝光点 ↔ 测试用例定位」四处的统一主键，生成后不可复用、不可回收。
   · **可拖拽控件白名单（本期，尽可能全）**：文本/按钮、输入框、图片/视频、容器与布局、列表与网格、单选/多选/开关/下拉选择/滑块/评分、日期与时间选择器、进度条/加载/Toast/弹窗、顶部与底部导航等（详见 `platform/平台需求概要.md` F13）。图表、地图、自定义绘制、复杂动画不在本期范围。
   · **Spec 交付格式**：统一 Markdown（`.md`）。
2. **来源标注**：所有产出标注 PRD 的 `document_id` + `revision_id`（飞书）/ 文件版本号。
3. **待澄清**：`[待澄清-Q#]` + 阻断等级（阻断/重要/建议），禁止自行脑补。
4. **追溯**：每个条目挂 REQ-ID，文末必附追溯表。
5. **术语一致**：一律使用 `baseline/术语表.md` 与 `领域模型.md`。
6. ★ **三态收敛**：任何被识别出的问题点，必须收敛为「需求 / 假设+理由 / 明确排除」三者之一。沉默的角落就是上线后坏掉的那一个。
7. ★ **来源标注**：完善后 PRD 的每段实质内容都要带来源标签；无来源的只能进《假设确认清单》并需 PM 确认。"行业惯例""我推测"都不是来源。
8. ★ **评审独立**：评审员不修改被评产物，输出 `READY` / `NOT-READY` + 逐条可核查证据；默认姿态是证伪。
9. ★ **循环有上限**：`S1↔S2` 回流默认最多 3 轮，计数写入 append-only 日志；超限则升级为「接受并记录 / 中止」。
10. ★ **回写原文件**：补充内容写回原 PRD 文件，回写前留原文快照，只写入已 Accept 的内容；回写只做「补充与澄清」，**不删除、不改写原文已有内容**，除非 PM 明确要求。

## 5 飞书取数（平台 S0 阶段复用）

全部 `--as user`，命令用法以 `lark-cli skills read lark-doc` 为准：

```bash
# 正文
lark-cli docs +fetch --doc "<URL>" --doc-format markdown --as user
# 内嵌表格（markdown 不会带出内容，必须主动补取）
lark-cli sheets +cells-get --spreadsheet-token <token> --sheet-id <sheet-id> \
  --range A1:H30 --as user \
  --jq '.data.ranges[0].cells | map(map(.value // "") | join(" | ")) | join("\n")'
# 白板流程图 → 图片 → 原生视觉读
lark-cli docs +media-download --token <token> --type whiteboard \
  --output <路径> --overwrite --as user
```

## 6 已知坑

- 飞书 PRD 的矛盾点常藏在**「正文规则」与「验收标准」两处不一致**，以及**被图片吞掉的表格字段清单**里——这正是 S1 门禁最该抓的。
- 内嵌表格是 sheet 对象，不在正文 markdown 里，不主动补取会整块丢字段。
- 白板只有缩略图，取不到结构化文本，必须视觉确认后再入基线。
- 接口字段名 ↔ App 映射、UI 页面 ↔ App 路由，是 5 份文档最容易漂移的两处，S5 校对必须做 diff。
