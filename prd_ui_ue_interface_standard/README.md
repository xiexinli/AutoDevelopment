# PRD / UI / UE / 接口 —— 前端 AI 直出代码交付标准

> **目标**：四份文档交付时，AI 能直接生成前端代码，且**不需要返工**。
> **手段**：标准条款全部原子化 + 编号化 → 可被 AI 与脚本校验 → 门禁通过才进入开发。

---

## 0. 核心命题：标准要"可校验"，而不只是"写得好"

上一版标准的问题是——条款是**给人读的散文**。人读了点头，AI 读了没法判定。

本版做了一件事：**把每条标准拆成一条带编号的原子规则**，每条规则必须能回答：

| 字段 | 含义 | 例 |
|---|---|---|
| `ID` | 唯一规则号 | `R-PRD-005` |
| `规则` | 一句可判定的话 | 每个字段必须有英文名 |
| `等级` | 不通过的后果 | 阻断 / 严重 / 警告 |
| `判定方式` | 谁来判、怎么判 | 机检 / AI检 / 人工 |

**只有原子化、可判定的规则，才能被 AI 稳定校验。** 这是本仓库所有内容的组织原则。

**当前规则总量：91 条** —— `R-PRD` 26 · `R-UI` 17 · `R-UE` 15 · `R-API` 22 · `R-X` 11。

## 1. 三层校验模型

| 层 | 手段 | 覆盖的规则 | 成本 | 触发时机 |
|---|---|---|---|---|
| **L1 机检** | `scripts/` 下的脚本 | 确定性规则：模糊词、编号、字段/错误码一致性 | 秒级、零成本 | 每次提交 / CI |
| **L2 AI 语义检** | LLM + 规则库 + 提示词 | 语义规则：状态覆盖、可空性、分支完整性 | 分钟级、低成本 | 门禁评审前 |
| **L3 人工评审** | 人 | 价值判断：需求是否合理、业务是否成立 | 高 | 门禁会 |

**分工原则**：能用脚本判的绝不交给 AI；能用 AI 判的绝不交给会。
AI 只负责"需要读语义才能判"的那部分——这也正是它不可替代的部分。

## 2. 门禁流程

```
文档产出
   ↓
① L1 机检        scripts/run_all.sh        → 阻断项 > 0 ？直接打回
   ↓ 通过
② L2 AI 校验     ai-validation/校验提示词.md → 输出结构化报告
   ↓ 通过
③ L3 人工评审    checklists/Ready门禁清单.md → 阻断项 = 0
   ↓ 通过
④ AI 直出代码
   ↓
⑤ 校验漏判 → 补规则 → 回到 ①   （规则库是活的，会进化）
```

**判定口径（关键）**：
- **阻断项 = 0** 才放行，严重项 > 3 不放行。
- AI 找不到证据 → **判不通过**，不判通过。
- 宁可误报，不可漏报——返工成本远高于多看一眼的成本。

## 4. 快速开始

```bash
# 0) 初始化：把模板复制成你的文档（只需做一次）
cp templates/PRD模板.md          docs/prd/PRD.md
cp templates/UI-UE标注模板.md     docs/ui/UI说明.md
cp templates/UI-UE标注模板.md     docs/ue/UE说明.md
cp templates/openapi模板.yaml     docs/api/openapi.yaml
cp templates/数据字典.csv         docs/数据字典.csv
cp templates/错误码文案表.csv     docs/错误码文案表.csv

# 1) 填写完毕
# 2) 跑机检
bash scripts/run_all.sh
# 3) 把 ai-validation/校验提示词.md 里的提示词 + 文档一起丢给 AI
# 4) 人工评审判定：checklists/Ready门禁清单.md
```

**依赖**：机检只需 Python 3（标准库）。
若接口用 YAML 格式，需要 `pip3 install pyyaml`；未安装时脚本会提示并跳过 YAML，
此时可改用 `.json` 格式的 OpenAPI，或直接安装依赖。

**验证脚本是否有效**：仓库里带了一份故意写错的示例，可以先跑一遍看效果：

```bash
bash scripts/run_all.sh examples/docs      # 应当报出 5 个阻断项
```

## 5. 单一真相源（本版最重要的改动）

散落在 Word / 飞书表格里的字段定义，是**跨文档不一致的根源**，也是 AI 幻觉的温床。

本版强制：字段与错误码**各收敛到一个 CSV 权威源**。

| 内容 | 权威源 | 谁必须服从它 |
|---|---|---|
| 字段名 / 类型 / 枚举 / 可空性 | `docs/数据字典.csv` | PRD 表格、OpenAPI、TS 类型、代码 |
| 错误码 / 文案 | `docs/错误码文案表.csv` | OpenAPI responses、前端错误处理、i18n |

PRD 里的字段表是权威源的**渲染结果**，不是另一个副本。
这样 `check_consistency.py` 才能做确定性 diff —— 一致性从"靠人盯"变成"靠机器判"。

## 6. 边界：AI 校验做不到什么

必须诚实说明，否则会给人虚假的安全感：

- ❌ 判断**需求本身是否合理**、商业逻辑是否成立
- ❌ 判断**设计稿是否美观**、是否符合品牌调性
- ❌ 判断**业务规则是否符合真实业务**（AI 只能判断它是否"表述完整"）
- ❌ 判断**优先级与排期**

**AI 校验的是"完整性、一致性、无歧义性"，不是"正确性"。**
前者是它可以做到 90%+ 的；后者永远需要人。

## 7. 规则库的演进

规则库不是一次性写完的。闭环是：

> 校验漏判了什么 → 补一条规则 → 下次不会再漏

每次 AI 直出代码出现返工，都要问一句：**这是哪条规则没写清楚？**
把它补进对应的 `R-XXX-xxx`。跑三个月，规则库会比任何专家评审表都好用。

### v2.1 变更（依据实跑校验）

对 Anthopia 移动端四件套实跑后发现 15 处规则盲区，已补齐。（其中 2 条由上一轮 L2 报告自己提出）

| 新增 | 规则 | 等级 | 判定 |
|---|---|---|---|
| R-PRD-021 | 数据字典列数与表头一致（列错位） | 阻断 | 机检 |
| R-PRD-022 | 状态机完整（枚举值都有进入/退出条件与页面表现） | 阻断 | AI检 |
| R-PRD-023 | 埋点事件清单完整 | 严重 | AI检 |
| R-PRD-024 | 交叉引用的目标章节真实包含所述内容 | 阻断 | 机检+AI检 |
| R-PRD-025 | 术语表禁止同义词全库反查（**只给候选，不给结论**） | 警告 | 机检+AI复核 |
| R-PRD-026 | 同一实体内带单位的字段口径一致 | 阻断 | 机检 |
| R-UI-016 | 断点区间互斥且完备，且与 PRD 一致 | 阻断 | 机检 |
| R-UI-017 | 设计稿链接真实可访问，非占位 | 阻断 | AI检 |
| R-API-019 | 非 200 响应与错误码表的 HTTP 状态一致 | 阻断 | 机检 |
| R-API-020 | 公开接口显式 `security: []` | 严重 | 机检 |
| R-API-021 | 非必填字段显式 nullable | 严重 | 机检 |
| R-API-022 | Mock 覆盖成功/错误/边界三类 | 严重 | AI检 |
| R-X-009 | PRD 文案都能在 UE 文案表找到 | 阻断 | 机检 |
| R-X-010 | 每个语言的文案只有一个权威源 | 严重 | AI检 |
| R-X-011 | 共享常量（断点/枚举/上限）跨文档一致 | 阻断 | 机检+AI检 |

同时修正一处**判定方式错配**：R-UI-015 原标为"机检"，改为"AI检"——
机检看到 `Figma：由设计团队提供` 这种占位句会判通过，只有 AI 能识别它在为空缺找理由。

**这一条是本轮最重要的教训**：机检全绿 ≠ 文档可用。
