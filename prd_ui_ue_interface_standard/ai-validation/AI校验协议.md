# AI 校验协议

> 规定"用 AI 校验文档"这件事的**输入、输出、判定口径与防幻觉约束**。
> 没有这份协议，AI 校验会退化成"读一遍然后说'看起来挺全的'"。

---

## 1. 定位

AI 校验负责 **L2 语义层**：
- ✅ 它擅长的：完整性、一致性、无歧义性、分支覆盖
- ❌ 它不擅长的：需求是否合理、业务是否正确、设计是否好看

**把 L1（机检）能判的东西交给 AI 是浪费，也是引入不确定性的行为。**

---

## 2. 输入契约

AI 校验的输入必须是**结构化的一组文档 + 明确的范围**：

```
输入：
  1. 规则库：standards/ 下四个规则表（或指定的规则 ID 子集）
  2. 待检文档：
     - docs/prd/*.md
     - docs/ui/*.md
     - docs/ue/*.md
     - docs/api/*.yaml
     - docs/数据字典.csv
     - docs/错误码文案表.csv
  3. 范围限定（可选）：仅校验 R-PRD-xxx / 仅校验某个 FR 编号
```

**范围必须限定。** 全量灌入会因上下文过长而漏检——这是 AI 校验最大的工程风险。

推荐分片方式：**按规则 ID 分片**，或**按需求编号分片**。

---

## 3. 输出契约

### 3.1 机器可读（JSON）

每条规则的判定产出一条记录：

```json
{
  "rule_id": "R-PRD-012",
  "level": "阻断",
  "status": "fail",
  "location": "docs/prd/订单模块.md#L142",
  "evidence": "该页仅描述了'有数据时的展示'，未提及空态与错误态",
  "issue": "页面状态覆盖不完整",
  "fix": "补充 加载/空/错误/无权限/极端数据 五类状态的展示说明"
}
```

`status` 取值：`pass` / `fail` / `uncertain` / `na`

### 3.2 人可读（Markdown 报告）

```
## 校验结果：PRD（docs/prd/）
阻断 3 · 严重 5 · 警告 2

### 🔴 R-PRD-012 页面状态覆盖不完整（阻断）
位置：订单模块.md#L142
证据：「列表中展示订单信息，按创建时间倒序」
问题：仅描述理想态，未定义 空/错误/无权限/极端数据 四种状态
建议：补充五类状态清单，并指明空态区分"首次为空"与"筛选后为空"
```

### 3.3 汇总

| 统计项 | 含义 |
|---|---|
| 阻断 / 严重 / 警告 数量 | 门禁判定依据 |
| 规则通过率 | `pass / (pass+fail)`，衡量文档成熟度 |
| `uncertain` 数量 | **必须为 0 才算校验完成**，否则需人工介入 |

---

## 4. 判定口径（防幻觉，最关键的一节）

AI 校验的可信度完全取决于这几条约束。**必须写进提示词，不可妥协。**

| # | 原则 | 说明 |
|---|---|---|
| 1 | **举证责任在文档** | AI 找不到证据 → 判 `fail`，**不判 pass**。文档必须自证完整 |
| 2 | **必须引用原文** | 每条判定附位置与原文片段；无法引用 → 判 `uncertain` |
| 3 | **禁止补全** | AI 不得把"文档没说"解释为"显然应该是"。只能报告缺失 |
| 4 | **禁止推测意图** | 不得写"作者应该是想……"。只判定文档**写了什么** |
| 5 | **不确定必须显式** | 允许 `uncertain`，**绝不允许静默放过** |
| 6 | **同一问题只报一次** | 避免同一缺失在 10 个页面里被报 10 遍淹没重点 |
| 7 | **不改文档** | AI 校验只做判定与建议，不回写。修改由人决定 |

**核心权衡：宁可误报，不可漏报。**
误报的代价是多看一眼；漏报的代价是开发返工。二者成本差一个数量级。

---

## 4.1 确定性规则 vs 启发式规则（工程上的关键区分）

不是所有规则都该以同样的方式执行。混淆这两类，结果就是**用噪声淹没真正的问题**。

| 类型 | 机器能给出的 | 典型规则 | 处理方式 |
|---|---|---|---|
| **确定性规则** | **结论**（pass / fail 可直接采信） | 列错位、字段名不一致、断点重叠、HTTP 状态冲突、可空性缺失 | 机检直接判定，无需 AI 复核 |
| **启发式规则** | **候选集**（必须再由 AI 或人判定） | 术语反查、模糊词、文案一致性 | 机检只产出候选，等级降为警告，结果聚合为一条 |

**两条硬性纪律**：

1. **同一问题只报一次。**
   本轮首次实跑产生 145 条阻断，其中 132 条是同一个问题在 38 个接口上的重复。
   聚合后收敛到 14 条才可用。重复的告警等于没有告警。

2. **启发式规则必须限制搜索域。**
   术语反查首次实现时未剔除术语表自身，每个禁止词都命中了它自己所在的那一行，
   31 条候选里 28 条是噪声。**规则写错比不写更糟**——它会训练出"忽略告警"的习惯。

## 5. 执行顺序

分五步，**顺序不可调换**（后面的步骤依赖前面的结果）：

```
① 结构完整性检查   章节/表头/字段是否齐全        → 不齐则直接返回，无需继续
② 机检结果注入     读取 scripts/ 的输出          → 让 AI 不重复判确定性项
③ 逐条规则语义判定 按规则 ID 分片，逐条出结论
④ 跨文档一致性     需要同时读多份文档的 R-X 规则
⑤ 汇总与门禁判定   统计 + 生成报告
```

---

## 6. 提示词工程约束

| 项 | 要求 |
|---|---|
| 温度 | 低（0 ~ 0.2） |
| 分片 | 按规则 ID 或需求编号分片，单次不超过 1 份文档全文 |
| 输出格式 | 强制 JSON schema，避免自由发挥 |
| 规则全文 | 提示词中**完整给出规则原文**，不要让 AI 去"理解标准精神" |
| 反例 | 每个提示词附 1 个正例 1 个反例，锚定判定尺度 |
| 复核 | 阻断项建议用**另一个模型或第二次调用**复核，降低单点误判 |

---

## 7. 迭代闭环

```
校验 → 发现漏判 → 补规则（R-XXX-0xx）→ 重跑 → 更准
```

判断"是否需要补规则"的信号：

- AI 直出代码后出现返工，而**没有任何规则命中它** → 补规则
- AI 反复把某个 `pass` 判成 `fail` → 规则表述不够可判定，改写规则
- 人评审总要额外补问同一类问题 → 该类问题应成为一条规则

**规则库不是文档，是资产。它应该随项目时间越来越厚。**

---

## 8. 边界声明（必须向业务方说明）

AI 校验通过 ≠ 文档正确。它只保证：

- 完整（该有的都有）
- 一致（各文档之间对得上）
- 无歧义（AI 能机械翻译）

它不保证：

- 需求合理
- 业务正确
- 设计美观

**这三件事仍然只能在 L3 人工评审里解决。**
