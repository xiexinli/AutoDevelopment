## C1. 需求本身是否成立、是否值得做

**已核实的证据**

- 对标产品为已上线的桌面端 v1.1.0，本机可运行，说明产品形态已被验证过一次。
- 桌面端实际使用痕迹可观察：首页展示账户积分余额、签到奖励弹窗、历史会话入口，说明积分与等级体系是真实在跑的功能，而非设想。
- 本版把桌面端 9 个功能域（账号与鉴权、首页、任务市场、任务协作、智能体中心、广场、身份与凭证、积分钱包、个人中心与设置）映射为移动端 9 个模块，未新增桌面端不存在的业务。

**需拍板的决策点**

| # | 问题 | 选项 A | 选项 B | 文档当前立场 |
|---|---|---|---|---|
| D-1 | 移动端定位 | 桌面端的伴随端（仅查看与轻操作） | 可独立走通完整闭环 | 按选项 B 设计，见 PRD 第 1 节目标 G-1 |
| D-2 | 首发范围 | 全量 9 模块 | 砍掉广场与钱包，先上 7 模块 | 按全量 9 模块编写，可按需裁剪并同步删减对应 FR |
| D-3 | 与桌面端账号关系 | 共用同一账号体系与数据 | 移动端独立账号 | 按共用设计（登录接口与用户实体同一套） |

> D-1 与 D-3 若选另一侧，PRD 第 1 节目标、第 2 节权限矩阵与接口契约的鉴权段需要重写，工作量约 1 天。

## C2. 业务规则是否符合真实业务

**已核实的证据**：PRD 第 5 节 20 条 `if-then` 规则，其中 6 条属于资金与状态的关键规则：

1. Draft 且已指派智能体 → 允许发布；
2. Draft 且点击发布 → 冻结 bountyAmount，状态置 Publishing；
3. NeedsAcceptance 且 isAccepted 为 true → 置 Settling，结算成功后置 Completed；
4. NeedsAcceptance 且发起争议 → 置 InDispute，赏金保持冻结；
5. Cancelled 且赏金已冻结 → 全额退回发布者；
6. deadlineAt 已过且未完成未取消 → 禁止启动。

**需拍板的决策点**

| # | 问题 | 说明 | 文档当前立场 |
|---|---|---|---|
| D-4 | 赏金冻结时点 | 是「点击发布即冻结」还是「启动执行才冻结」 | 点击发布即冻结（规则 2） |
| D-5 | 争议仲裁主体与时限 | 文档只定义进入 InDispute 与赏金保持冻结，未定义由谁仲裁、多久出结果、超时怎么处理 | 未定义，需补规则 |
| D-6 | 取消的扣费规则 | 文档定义为全额退回，未区分「已开始执行后取消」是否扣除部分 | 一律全额退回 |
| D-7 | 五级等级阈值 | 文档把升级阈值交由接口下发（minCompletedTaskCount / minCredibilityScore），未在文档中固定具体数值 | 未固定，需业务给出 L1 至 L5 的阈值表并回填 PRD |
| D-8 | 信誉分的加减规则 | 文档只定义取值 0 至 100，未定义何时加、何时减、单次幅度 | 未定义，需补规则 |
| D-9 | 智能体赏金定价 | 智能体有 priceAmount 与 priceUnit，但任务赏金由发布方自定；两者关系是「赏金覆盖服务费」还是「另外计费」 | 未定义，需明确 |

> **D-5、D-7、D-8、D-9 属于真实业务规则缺口**，不是文档表述问题：AI 无法从对对标产品的观察中得出这些数值，必须由业务方给出。建议在门禁会上直接定值。

## C3. 设计稿是否符合品牌与审美要求

**已核实的证据**

- UI 说明第 2 节的 Token 基线来自对标产品的真实样式表：主色 `#7c3bff`（浅色）/ `#a070ff`（深色）、页面底色 `#ffffff` / `#000000`、卡片底色 `#f7f7f7` / `#141414`、成功 `#2bc235`、危险 `#f7594b`、信息 `#1a77ff`，产品为深色优先。
- 间距采用 4 基准刻度，圆角与阴影已枚举，动效时长与缓动曲线已给出具体值。

**需拍板的决策点**

| # | 问题 | 说明 |
|---|---|---|
| D-10 | 设计稿链接 | L2 警告项 F-1：Figma 链接尚未挂载，需设计团队提供后回填 `docs/ui/UI说明.md` 第 1 节 |

## C4. 优先级与排期是否可接受

**已核实的依赖关系（来自接口与页面跳转）**

```
账号与会话（无前置）
   └─ 首页（依赖用户资料、我的任务、通知）
   └─ 任务市场（可游客浏览）
        └─ 任务协作（依赖智能体指派）
             └─ 智能体中心（被任务协作依赖）
   └─ 身份与等级（依赖任务完成产生凭证）
   └─ 积分钱包（依赖结算产生流水）
   └─ 广场（可独立并行）
   └─ 个人中心与设置（依赖账号）
```

**建议排期（供讨论，非结论）**

| 批次 | 模块 | 理由 |
|---|---|---|
| 第一批 | 账号与会话、首页、个人中心与设置 | 无对外依赖，可先行 |
| 第二批 | 任务市场、智能体中心 | 只读为主，可与第一批并行开发 |
| 第三批 | 任务协作 | 状态机最复杂（18 个状态），依赖第二批 |
| 第四批 | 身份与等级、积分钱包 | 依赖任务协作产生数据 |
| 第五批 | 广场 | 可任意时点并行插入 |

**需拍板的决策点**：D-13 首发批次划分（建议第一批 + 第二批一起上）；D-14 是否接受广场延后。

## C5. 是否存在文档未覆盖的隐性需求

**已识别的候选隐性需求（文档当前未覆盖）**

| # | 隐性需求 | 为什么重要 | 建议 |
|---|---|---|---|
| E-1 | 实名认证前置 | 文档把 KYC 列为「不做」，但涉及赏金收付；未实名用户能否发布或承接任务未定义 | 建议定义：未实名仅可浏览，不可发布与承接 |
| E-2 | 内容审核 | 广场话题、任务描述、对话消息三处均需审核策略，文档未定义机审、人审、敏感词与举报入口 | 建议补一条业务规则与一个错误码 |
| E-3 | 风控与刷单 | 文档未定义同一用户自发布自承接、异常高频接单的拦截 | 建议在业务规则补 1 至 2 条 |
| E-4 | 多端登录态 | 桌面端与移动端是否互相踢下线未定义 | 建议明确为「互不影响，多端并存」或「单端在线」 |
| E-5 | 历史数据兼容 | 桌面端既有任务与凭证在移动端的状态映射 | 文档已用 18 状态别名兼容大小写与下划线写法，建议复核与线上真实取值是否一致 |
| E-6 | 消息推送 | 文档只定义站内通知，未定义推送通道与免打扰 | 建议补充推送触发点清单 |

**需拍板的决策点**：D-15 上述 E-1 至 E-6 中，哪些纳入 V1.0，哪些明确延后。
