**三者与本报告不矛盾，但都不完整。** 它们依据的是 v2.0 的 76 条规则，
而本轮扩到 91 条后新增的 15 条在这三份旧报告里**没有任何一条被检查过**
（经检索：旧 L2 报告全文出现 `NeedsSign`/`AgreementPending`/`NeedsReSign`/`SettleFailed`
各 0 次，`重叠` 0 次，`security` 0 次，`列错位` 0 次）。

**因此上一轮的"有条件通过"结论应暂缓采信**，待 P0 修复后重跑 L1（v2.1）与 L2 再定。

这也正是本轮任务的价值所在：**旧报告不是错了，是规则库还不够密。**


**核心教训**：

1. **机检全绿 ≠ 文档可用。** 本轮 v2.0 规则 0 阻断，但实际有 8 个阻断级问题。
   凡"一句话说得像那么回事、实际什么都没有"的问题，只能靠 AI 语义检。
2. **枚举穷举 ≠ 状态机完整。** 要求"枚举值列全"只是第一步，
   更要紧的是要求"每个枚举值都有进入/退出条件"。前者机检能做，后者必须 AI 检。
3. **文件存在 ≠ 引用有效。** 交叉引用要验到"目标章节是否真的包含所述内容"这一层。
4. **区间重叠是最隐蔽的规格缺陷。** 每一条单看都对，合起来无法实现。
5. **同类问题必须聚合报告。** 首次实跑产生 145 条阻断，其中 132 条是同一问题在
   38 个接口上的重复。按协议第 6 条聚合后收敛到 14 条，才具备可读性与可操作性。

### ✅ P0-2 任务状态机补齐

**修复**：PRD 新增 §5.1「任务状态机」，定义全部 18 个状态的进入条件、页面可执行动作、
可转移目标与视觉基调；`status` 枚举在 PRD 中的出现数由 **7 个为 0** 变为 **0 个为 0**。

**语义来源**：对标产品 Anthopia 桌面端 v1.1.0（`/Applications/Anthopia.app`，Electron 构建）。
从其 `app.asar` 中提取到权威依据，非推测：

- **状态标签**：`taskCard.status` / `taskBoard.card.status` 两份 i18n 资源
- **逐状态可用动作**：任务卡动作映射表 —— 例如
  `Draft:[edit, sign_launch]`、`NeedsSign:[view_agreement, sign_agreement]`、
  `NeedsAccess:[grant_access]`、`NeedsMaterials:[add_materials]`、`Paused:[resume]`、
  `NeedsAcceptance:[open_dispute, review_delivery]`、`NeedsReSign:[re_sign_agreement]`、
  `Completed/Cancelled/Failed:[create_again]`
- **状态说明文案**：如「任务已暂停，Agent 执行已停止」「结算流程失败，可重试」
  「{agent} 需要获得批准才能访问所选资源」
- **视觉基调**：状态→样式类映射（draft / matching / running / failed / completed）

**同时修正**：FR-016 的「结果」原写「任务状态变为 Publishing」，与状态机不符——
已改为「先变为 NeedsSign，签署完成后转为 Publishing」。

> ⚠️ **这一处需要产品确认**：FR-016 的改动把「签署并发布」拆成了两步
> （Draft → NeedsSign → Publishing），依据是对标产物中 `sign_launch` 与
> `sign_agreement` 是两个独立动作。若移动端产品决定合并为一步，
> 应改回「Draft → Publishing」，并把 `NeedsSign` 标注为桌面端专用状态。

### ✅ P0-3 HTTP 状态契约冲突

**修复方案**：保留错误码文案表的状态码语义作为权威，**反向补齐 OpenAPI 的响应声明**。

在 `components/responses` 新增 9 个可复用响应组件，并为 35 个接口补齐其
`x-error-codes` 对应的全部非 200 响应：

| HTTP | 新增响应声明的接口数 |
|---|---|
| 400 | 7 |
| 401 | 33 |
| 403 | 6 |
| 404 | 8 |
| 409 | 11 |
| 413 | 2 |
| 415 | 2 |
| 429 | 6 |
| 500 | 38 |

同时在 `info.description` 的全局约定中明确三条，消除歧义：

1. HTTP 状态码按错误语义返回（400/401/403/404/409/413/415/429/500），纯业务规则失败时也可为 200
2. **无论 HTTP 状态码为何，响应体始终是统一包体**；`code` 是业务判断的唯一权威依据
3. 前端拦截器约定：401 → 静默刷新 token 并重放；5xx → 按「是否重试」列自动重试 1 次；其余读 `code`

备份：`/tmp/openapi.json.bak`。验证：`R-API-019` 已消失。
