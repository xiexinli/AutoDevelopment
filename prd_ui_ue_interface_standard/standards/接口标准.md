# 接口标准（R-API）

## 0. 前端独有的杠杆

接口只要标准化成 **OpenAPI 3.x**，就能：

```
openapi.yaml  ──[openapi-typescript]──▶  types.ts  ──▶  AI 直接写页面
```

**类型自动生成**意味着 AI 不可能把字段名写错、把可空性写错。
这是前端相比其他端最大的优势，**不用就是浪费**。

所以本标准的第 1 条就是硬的：**不接受非 OpenAPI 的接口描述**（Word 表格、飞书表格、Postman 集合都不行）。

---

## 1. 统一响应包体

全项目一致，不允许某个接口"特事特办"：

```json
{ "code": "OK", "message": "success", "data": { }, "traceId": "..." }
```

- `code` 为**业务码字符串**（不用纯 HTTP 状态码表达业务失败）
- 业务成功与 HTTP 200 解耦：业务失败可返回 HTTP 200 + `code != OK`

---

## 2. 字段规则（与 `数据字典.csv` 强绑定）

| 项 | 要求 |
|---|---|
| 英文名 | 与 `docs/数据字典.csv` **完全一致**，禁止 `orderNo` vs `order_no` |
| 枚举 | **全量列举**。没列全 → TS 只能生成 `string` → 类型保护失效 |
| 可空性 | 明确 `nullable` / `required`。三者语义不同：`null` / `""` / 字段缺失 |
| ID | 类型必须 `string`（`Number` > 2^53 丢精度） |
| 金额 | 单位（分/元）+ 传输类型（string）写进 description |
| 时间 | ISO 8601 + 时区，写进 description 与 example |
| 布尔 | 统一 `is` / `has` 前缀，不用 `0/1` |

---

## 3. 错误码

- 每个接口必须**枚举全部错误码**，不能只给 200 示例
- 每个错误码必须在 `docs/错误码文案表.csv` 中有 **对应用户文案**
- 没有文案 → AI 只能写 `message.error('请求失败')`

---

## 4. 全局约定（写进 `info.description`）

- 分页：参数名（`page`/`pageSize`）+ 返回结构（`list`/`total`/`hasMore`）全局统一
- 鉴权方式：Bearer / Cookie / CSRF
- 前端专属协议：CORS 策略、文件上传下载方式、WebSocket / SSE 事件定义（若有）
- 空值约定：`null` / `""` / 缺省 三者的使用规则

---

## 5. 示例与 Mock

- 每个接口提供**完整示例**：正常 + 至少一个错误 + 一个边界（空列表 / 超长）
- 提供 Mock 服务或 Mock 数据文件，**让前端不等后端**

---

## 6.1 响应定义必须与错误码表对齐（R-API-019，本轮新增）

本轮校验发现一处**契约级冲突**：

- 错误码文案表声明了 HTTP 状态：`400 / 401 / 403 / 404 / 409 / 413 / 415 / 429 / 500`
- 但 OpenAPI 里 **38 个操作全部只声明了 `200` 响应**

这意味着接口契约是自相矛盾的：错误码表说有 404，接口说只有 200。
前端据此写拦截器时，无法判断"哪些接口会返回 403"——只能全接口统一兜底，
于是"权限不足"在有的页面是页面级、有的页面是 toast。

**判定口径**：某错误码在文案表中标注的 HTTP 状态不是 200，则该错误码所在接口必须声明对应的 HTTP 响应。

如果团队约定"业务失败一律 HTTP 200 + `code != OK`"，那就**把文案表里的 HTTP 状态列改成 200**，
两边必须一致——不一致本身就是问题，方向不重要。

---

## 6.2 鉴权必须显式（R-API-020，本轮新增）

本轮发现 6 个接口（`/auth/captcha`、`/auth/register`、`/auth/login` 等）**完全没有 `security` 字段**。

它们确实是公开接口——但"没写"和"是公开的"在契约里长得一模一样。
前端生成请求层时无法区分"这个接口不需要带 token"与"这个接口漏写了鉴权"。

**约定**：
- 公开接口：`security: []`
- 鉴权接口：`security: [{ bearerAuth: [] }]`

---

## 6.3 可空性必须显式（R-API-021，本轮新增）

本轮发现 `ProfileUpdateRequest` 有 4 个字段，`required` 为空，其中 3 个既不在 required 也没标 `nullable`。

部分更新（PATCH/PUT）场景下这一点尤其致命：

```
不写 → TS 生成 nickname?: string      （可传可不传，但不代表能传 null）
不写 → TS 生成 nickname: string|null  （如果误标 nullable）
```

**"不传"与"传 null"是两种语义**——前者表示"不修改该字段"，后者表示"把该字段清空"。
混淆的后果是用户清空昵称，服务端却当成"未修改"，什么都没发生。

每一个非必填字段必须**二选一**：写进 `required`，或标注 `nullable: true`。

---

## 6.4 Mock 覆盖度（R-API-022，本轮新增）

本轮 Mock 文档给了 7 个成功样例与 3 个错误样例，而契约有 38 个操作。

Mock 的价值在于让前端**不等后端**，所以覆盖度就是它的全部价值。
判定口径：每个接口至少有 成功 / 业务错误 / 边界（空列表或超长） 三类样例。
OpenAPI 的 `examples` 里已有 `success` / `businessError` / `boundary` 三段的，算通过。

## 7. 跨文档规则（R-X）

以下规则需要**同时读多份文档**才能判定，属于一致性校对：

| ID | 规则 | 等级 | 判定方式 |
|---|---|---|---|
| R-X-001 | 每个 `FR-xxx` 至少映射到一个 UI 页面 | 阻断 | AI检 |
| R-X-002 | PRD 字段 ↔ API 字段双向一致（无孤立字段） | 阻断 | 机检 |
| R-X-003 | 每个错误码有 UI 展示形态 | 阻断 | 机检 |
| R-X-004 | UI 每个交互元素有 UE 行为定义 | 严重 | AI检 |
| R-X-005 | 枚举值在 PRD / UI / API 三处一致 | 阻断 | AI检 |
| R-X-006 | 无孤立编号（引用了不存在的编号） | 严重 | 机检 |
| R-X-007 | 术语一致，无同义词漂移（订单/单子/单据） | 警告 | AI检 |
| R-X-008 | 路由参数名与数据字典字段名一致 | 严重 | AI检 |
| **R-X-009** | **PRD 中出现的全部用户可见文案都能在 UE 文案表中找到** | **阻断** | **机检** |
| **R-X-010** | **每个目标语言的文案有唯一权威来源（i18n 源唯一）** | **严重** | **AI检** |
| **R-X-011** | **共享常量（断点/枚举/数量上限）跨文档取值一致** | **阻断** | **机检+AI检** |

---

## 7.1 文案只能有一个源（R-X-009 / R-X-010，本轮新增）

本轮发现两类问题：

**第一类**：PRD 第 4 节页面状态表里写的文案，有 2 条在 UE 文案表中不存在——
「没有符合条件的凭证」「没有符合条件的流水」。
而 UI 第 3 节明明给"凭证列表页""流水列表页"勾选了"空（筛选后）☑"。
**页面有状态、状态没文案**，AI 只能自己编一句。

**第二类**：i18n 的权威源不唯一。
- PRD 第 9 节说："文案来源为 `docs/ue/UE说明.md` 的文案表"
- UI 第 9 节说："英文文案在相同画板中并列出稿"
- 而 UE 文案表**只有中文**

同一份文案有"文案表"和"设计画板"两个源，就等于没有源。

**判定口径**：
1. 凡在 PRD 中以「」标注的文案，必须能在 UE 文案表中原样检索到；
2. 每个目标语言（zh-CN / en-US）必须指向**唯一**的权威文件与章节。

---

## 7.2 共享常量必须跨文档一致（R-X-011，本轮新增）

断点、枚举取值、数量上限（如"pageSize 最大 100"、"未读角标 99+"）这类常量，
一旦在多个文档里各写一份，就一定会漂移。

本轮断点表就是活例：PRD 与 UI 各写一版，两版都重叠，且互相不一致。

**约定**：这类常量集中在**一个**权威文件里定义（推荐放进 `数据字典.csv` 旁），
其他文档只引用不复制。机检负责比对取值是否一致。
